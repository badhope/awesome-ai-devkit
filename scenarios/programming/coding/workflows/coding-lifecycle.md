# 通用编码生命周期工作流

> 适用：任何编码任务（脚本/CLI/库/服务/算法），不绑定技术栈。核心是**把事情写对、测对、交付对**。

## 流程总览

```
requirements → design → implement → test → review → commit
```

---

## Stage 1: 需求澄清

**角色**: 主导（架构师 / 技术负责人），协作（需求发起人）

**输入**:
- 任务描述（一句话或详细 PRD）
- 已知约束（技术栈、性能、兼容性）

**产出**:
- 可执行验收标准（完成定义 DoD）
- 边界与异常场景清单
- 明确"不做"事项

**验收条件**:
- [ ] 有清晰的"完成定义"
- [ ] 边界/异常场景已列出
- [ ] 技术栈与约束已确认

---

## Stage 2: 方案设计

**角色**: `architect-system-designer`

**输入**:
- Stage 1 的需求与验收标准
- 现有代码结构

**产出**:
- 简短技术方案（接口/数据结构/模块划分）
- 架构决策（ADR，必要时）

**验收条件**:
- [ ] 方案覆盖所有验收点
- [ ] 数据结构/接口已定义
- [ ] 无重复造轮（复用现有库/工具）

---

## Stage 3: 编码实现

**角色**: `backend-api-developer` / `frontend-ui-developer`（按需）

**输入**:
- Stage 2 方案

**产出**:
- 实现代码（语言无关）
- 单元测试覆盖核心路径

**实现顺序**:
1. 核心逻辑/数据结构
2. 对外接口
3. 边界与异常处理
4. 单元测试

**验收条件**:
- [ ] 核心路径实现
- [ ] 单元测试通过
- [ ] 无硬编码密钥/凭证

---

## Stage 4: 测试验证

**角色**: `test-qa-engineer`

**输入**:
- Stage 3 代码与单元测试

**产出**:
- 全量测试运行结果
- 边界/异常用例补充

**验收条件**:
- [ ] 全量测试通过
- [ ] 边界用例覆盖
- [ ] 关键路径无遗漏

---

## Stage 5: 代码审查 + 安全检查

**角色**: `code-reviewer`、`security-review-engineer`

**输入**:
- Stage 3/4 的代码与测试

**产出**:
- Review 结论（approved / 修改意见）
- 安全审查结果

**审查清单**:
- [ ] 实现是否符合方案
- [ ] 边界与错误处理完善
- [ ] 无注入 / 硬编码密钥 / 资源泄漏
- [ ] 测试覆盖修改路径

**验收条件**:
- [ ] 无安全高危漏洞
- [ ] lint 无 error
- [ ] 审查意见已处理

---

## Stage 6: 提交与交付

**角色**: `agent`（实施者）

**输入**:
- 通过审查的代码

**产出**:
- 符合规范的提交
- CHANGELOG 更新
- 记忆持久化（如有决策）

**验收条件**:
- [ ] 提交信息规范
- [ ] CHANGELOG 已更新
- [ ] 工作区干净

---

## 异常流程

| 异常场景 | 处理方式 |
|---------|---------|
| 需求不清晰 | 返回 Stage 1 澄清 |
| 方案不合理 | 返回 Stage 2 重新设计 |
| 测试失败 | 返回 Stage 3 修复后重测 |
| 审查不通过 | 返回 Stage 3 修复后重审 |
| 发现安全漏洞 | 立即修复，触发 incident-response 工作流 |
